# URY_RU_Fiscal — детальный проект модуля

Модуль фискализации для URY-RU. Реализует требования **54-ФЗ**: каждый расчёт
с покупателем фиксируется на ККТ, чек передаётся в ОФД, данные уходят в ФНС.

## 1. Цель и границы

**Внутри модуля:**
- Абстракция фискального драйвера (АТОЛ, ШТРИХ-М и любые будущие)
- Сборка фискального документа (чека) из `POS Invoice` по ФФД
- Очередь + retry + офлайн-режим
- Журнал фискальных чеков, привязка к заказам
- Смены кассы (открытие/закрытие), отчёты

**За пределами модуля (не наша зона):**
- Сама ККТ (железо), прошивка, регистрация в ФНС
- ОФД как сервис (мы только передаём чек в ККТ, ККТ сама шлёт в ОФД)
- Оплата/эквайринг — это модуль `URY_RU_Payments`

## 2. Нормативная база (что нужно знать)

- **54-ФЗ** — закон о применении ККТ. Обязанность: фискализировать каждый расчёт.
- **ФФД** (формат фискальных данных) — протокол передачи чека в ККТ:
  - **1.05** — устаревший, для услуг без маркировки
  - **1.1** — основной сейчас
  - **1.2** — обязателен для маркированных товаров (Честный знак), поддержка нужна для `URY_RU_Marking`
- **Типы фискальных документов** (тег 1059 «признак расчёта»):
  - Приход (продажа) — `sell`
  - Возврат прихода — `sell_return`
  - Расход / возврат расхода
  - Чек коррекции (при ошибках, сбоях)

## 3. Ключевые реквизиты чека (ФФД 1.1/1.2)

| Реквизит | Описание | Источник в URY |
|----------|----------|----------------|
| Сумма | итог чека | `invoice.grand_total` |
| Признак расчёта | приход/возврат | операция |
| Признак способа расчёта | полный расчёт/аванс/кредит | тип операции |
| Тип оплаты | наличные / электронные / предоплата | `invoice.payments[].mode_of_payment` |
| Ставка НДС | 20% / 10% / 0% / без НДС / расч. 20/120, 10/110 | маппинг из `Sales Taxes and Charges` |
| Наименование | название позиции | `invoice.items[].item_name` |
| Кол-во, цена | | `items[].qty`, `items[].rate` |
| Признак предмета расчёта | товар/услуга/работа | поле Item (доработка) |
| Регистрационный № ККТ (РНМ) | выдаёт ФНС | настройка ККТ |
| Заводской № (ЗН), ФН | | настройка ККТ |

## 4. Архитектура

Повторяет паттерн URY `PaymentTerminalProvider` — интерфейс + реестр + honest-failure.

```
POS Invoice (on_submit)
        │  ury_ru.ury_ru.URY_RU_Fiscal.hooks.on_submit
        ▼
  build_receipt_from_invoice()      ← сборка чека по ФФД (receipt.py)
        │
        ▼
  enqueue_fiscal_receipt()          ← асинхронная очередь (frappe.enqueue)
        │
        ▼
  FiscalDriver (fiscal_driver.py)   ← интерфейс
        │
        ├── SimulatedFiscalDriver   ← тесты/демо (возвращает фейковые ФД/ФПД)
        ├── AtolFiscalDriver        ← АТОЛ (DTO 10.x, JSON по TCP/HTTP)
        └── ShtrihMFiscalDriver     ← ШТРИХ-М (протокол ШТРИХ-М по TCP)
        │
        ▼
  ККТ ──► ОФД ──► ФНС
        │
        ▼
  URY RU Fiscal Receipt (журнал: ФД, ФПД, статус, ссылка на инвойс)
```

## 5. Компоненты (файлы)

| Файл | Назначение |
|------|------------|
| `fiscal_driver.py` | Абстрактный `FiscalDriver` + реестр `register_fiscal_driver()` / `get_fiscal_driver()` |
| `receipt.py` | `build_receipt_from_invoice(doc)` — POS Invoice → канонический чек ФФД |
| `fiscal_hooks.py` | `doc_events`: `on_submit` (продажа), `on_cancel` (возврат/аннулирование) |
| `drivers/simulated.py` | Эмулятор ККТ для тестов и демо |
| `drivers/atol.py` | Заглушка драйвера АТОЛ (честный NotImplemented + TODO по DTO 10.x) |
| `drivers/shtrih_m.py` | Заглушка драйвера ШТРИХ-М |
| `doctype/` | Настройки, ККТ, журнал чеков |

## 6. Модель данных (Doctype)

### URY RU Fiscal Settings (singleton)
- `driver` — Select: Simulated / ATOL / Shtrih-M
- `fiscal_format` — Select: ФФД 1.05 / 1.1 / 1.2
- `offline_mode_enabled`, `retry_count`, `retry_delay`
- Дочерняя таблица `НДС маппинг`: `account_head → ставка ФФД` (20%, 10%, 0%, без НДС, 20/120, 10/110)

### URY RU KKT (кассовый аппарат)
- `kkt_model`, `serial_number` (ЗН), `fiscal_accumulator` (ФН), `reg_number` (РНМ)
- `connection` (адрес/порт/токен драйвера), `ofd` (ОФД), `address` (адрес расчёта)
- `pos_profile` / `restaurant` — привязка к точке

### URY RU Fiscal Receipt (журнал)
- `pos_invoice` (Link), `receipt_type` (sell/sell_return/correction)
- `amount`, `fiscal_document_number` (ФД), `fiscal_sign` (ФПД)
- `status` (Pending / Sent / Confirmed / Failed / Offline), `error`, `retries`
- `shift` — ссылка на смену

## 7. Поток продажи (happy path)

1. Кассир пробивает заказ → `POS Invoice` → submit
2. Хук `on_submit` → `enqueue_fiscal_receipt(invoice)`
3. Worker: `build_receipt_from_invoice()` → чек ФФД
4. `get_fiscal_driver().register_receipt(чек)` → ККТ печатает чек
5. ККТ возвращает `{fiscal_document_number, fiscal_sign}` → сохраняем в журнал
6. ККТ асинхронно шлёт в ОФД → ФНС

## 8. Офлайн и отказоустойчивость

- Если ККТ недоступна — чек уходит в очередь, статус `Offline`, retry с backoff
- ККТ физически поддерживает офлайн (ФН хранит чеки до 30 дней) — мы лишь не теряем задачу
- Лимит `retry_count`, после — статус `Failed` + алерт кассиру
- Возврат (`on_cancel` / `is_return`) → `receipt_type = sell_return`, обязательная ссылка на исходный ФД

## 9. НДС маппинг (критично)

ERPNext хранит налоги как строки `Sales Taxes and Charges` (account_head + rate).
Для ФФД нужна ставка по каждой позиции:

- 20% → `vat20`, 10% → `vat10`, 0% → `vat0`
- «без НДС» → `none`
- расчётные 20/120, 10/110 — для позиций, где НДС в цене

Маппинг задаётся в `URY RU Fiscal Settings` (дочерняя таблица). Фолбэк: если позиция
не сопоставлена — `none` + warning в лог (не блокирует продажу, но помечается).

## 10. АТОЛ (особенности драйвера)

- **Atol Driver 10.x** — единый JSON-протокол (DTO) для всех моделей АТОЛ
- Общение: TCP/IP к службе драйвера, или HTTP (для смарт-терминалов АТОЛ 15Ф/17Ф)
- Команды: `openShift`, `closeShift`, `registerReceipt` (sell/sellReturn), `getStatus`
- Ответ: `{fiscalDocumentNumber, fiscalSign, total, ...}`

## 11. ШТРИХ-М (особенности драйвера)

- Протокол ШТРИХ-М по TCP, либо драйвер «ШТРИХ-М: ККТ»
- Команды: открыть/закрыть смену, пробить чек, возврат, отчёт о состоянии
- Модели: ШТРИХ-М-01Ф, ШТРИХ-ЛАЙТ, ШТРИХ-М-02Ф и др.

## 12. Тестирование

- `SimulatedFiscalDriver` — эмулятор, возвращает детерминированные ФД/ФПД
- Юнит: `build_receipt_from_invoice` на фикстурах (ставки НДС, типы оплат, возвраты)
- Интеграция: submit инвойса → чек в журнале → статус Confirmed
- Реальные ККТ — только на стенде с железом (не в этом окружении)

## 13. Принятые решения (владелец, 2026-08-24)

1. **ФФД 1.2** — не в этом модуле. Поддержка ФФД 1.2 (маркировка) живёт в `URY_RU_Marking`.
   Здесь остаётся ФФД 1.05 / 1.1.
2. **Смена кассы** — своя модель `URY RU Fiscal Shift` (не переиспользуем POS Opening/Closing Entry).
   API: `fiscal_shift.open_shift()` / `close_shift()`.
3. **Чек коррекции** — нужен UI. Реализован doctype `URY RU Fiscal Correction` (Desk-форма),
   на submit драйвер пробивает чек коррекции (`register_correction`).
